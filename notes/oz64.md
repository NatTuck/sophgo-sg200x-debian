# Pine64 Oz64 on the Sophgo SG200x Debian image

Notes gathered 2026-09-27 while trying to get the onboard WiFi working on a
Pine64 Oz64 running scpcom's Duo S Debian image.

## TL;DR

- There is **no Oz64-specific Linux image** anywhere. The "Oz64 Debian" that
  RuyiSDK tests is literally scpcom's Milk-V **Duo S** image
  (`duos-e_sd.img.lz4`), which is what this board is already running.
- Onboard WiFi does not work because:
  1. The AIC8800 driver fails at bring-up
     (`aicbsp: fail to set AIC_WIFI power state to 1`) and never creates
     `wlan0`. The SDIO WiFi card never enumerates (`mmc1` has no card).
  2. Even if it enumerated, the image ships **no AIC8800DC firmware**. Oz64
     uses an **AIC8800DC**; the image only carries AIC8800 / AIC8800D80 blobs.
- The upstream firmware repo `scpcom/aic8800-sdio-firmware` **does** now
  contain an `aic8800DC/` directory, but the image build (`addon.mk`) only
  installs `aic8800/` and `aic8800_and_aic8800D80/`. So the correct blobs are
  never packaged.

## Board / hardware facts

- Board: Pine64 **Oz64**, SoC **Sophgo SG2000** (RISC-V C906 + Arm A53 + 8051).
- WiFi/BT: **AIC8800DC** (2.4 GHz WiFi6, BT 5.2). Confirmed by the PINE64 wiki
  + datasheet links:
  - https://wiki.pine64.org/wiki/Oz64
  - AIC8800DC datasheet linked from
    https://pine64.org/documentation/Oz64/Datasheets/
- Ethernet: 10/100 via `end0`. USB gadget NIC via `usb0`.

## What the running system actually is

- Image: scpcom `sophgo-sg200x-debian`, release **v1.9.13**
  (`/boot/ver` = `duos-e_sd-v1.9.13.img`).
  - https://github.com/scpcom/sophgo-sg200x-debian/releases
- Kernel: `5.10.260-20260911-7+duos` (riscv64). `loglevel=0` on the cmdline,
  so a lot of early boot dmesg is quiet.
- Device tree model: **`Milk-V DuoS`** (`compatible = cvitek,cv181x`).
  So the board is booting the Duo S DTB, not an Oz64 DTB.
- `/boot/board` says `id=maixcam name=MaixCAM` (generic/default board id from
  the shared packaging — not meaningful for this board).
- Rootfs: `/dev/mmcblk0p2` ext4 rw, `/boot` on `/dev/mmcblk0p1` vfat.
- `/mnt/system/ko/5.10.260-20260911-7+duos/3rd/` holds the vendor kernel
  modules (loaded by `/etc/init.d/S25wifimod`).

## Side quest: hostname resets on reboot

Not WiFi, but figured out here: `/etc/init.d/S10uuid` runs every boot and
rewrites `/etc/hostname` (and `/etc/hosts`) from a device-key hash:

```
prefix=duos                       # from /boot/hostname.prefix
new_hostname=${prefix}-$(sha512sum /device_key | head -c 4)
```

So editing `/etc/hostname` is pointless. Persistent overrides:

- Full hostname: `echo NAME | sudo tee /boot/hostname`
- Just the prefix: `echo PREFIX | sudo tee /boot/hostname.prefix`

Same script also sets the ethernet MAC (`/boot/eth.mac` overrides).

## WiFi investigation details

### Interfaces / modules

- `ip link`: only `lo`, `end0`, `usb0`, `tunl0`. **No `wlan0`.**
- `lsmod`: `aic8800_bsp`, `8733bs`, `cfg80211`.
- Module identities (from `riscv64-linux-gnu-strings`):
  - `aic8800_bsp.ko` -> `description=AIC BSP`
  - `aic8800_fdrv.ko` -> `description=RivieraWaves 11nac driver for Linux cfg80211`
  - `8733bs.ko` -> `description=Realtek Wireless Lan Driver` (i.e. **RTL8733BS**,
    a Realtek part; irrelevant to Oz64 — it's a Duo S variant option).

### Boot failure

`dmesg` shows the AIC BSP failing to power up the WiFi subsystem:

```
aicbsp: aicbsp_set_subsys, subsys: AIC_WIFI, state to: 1
aicbsp: aicbsp_platform_power_on
aicbsp: aicbsp_set_subsys, fail to set AIC_WIFI power state to 1
AICWFDBG(LOGERROR)  rwnx_mod_init, set power on fail!
```

- `aic8800_fdrv` is **not** present in `lsmod` afterwards -> it failed and
  unloaded. `8733bs` stayed loaded but is for the wrong silicon.
- `aic8800_bsp` has no gpio/ioremap/regulator imports (only `sdio_*`), so its
  "platform power on" is ultimately gated on the SDIO card being present /
  the host-side callback; with no card on `mmc1` it fails.

### No SDIO card

- `/sys/bus/mmc/devices/` contains only `mmc0:0001` (the microSD).
- `mmc1` (`wifi-sd@4320000`, alias points at the SDIO host) exists, driver
  `cvi`, but has **no card** and no `dmesg` lines.
- DT: `wifi-sd@4320000`, `compatible = cvitek,cv181x-sdio`, `status = okay`.
- DT has a **gpio-hog** named `wifi_pwr`, `output-high`, under
  `/proc/device-tree/gpio@03020000/gpio-controller@0/`.
  - In `/sys/kernel/debug/gpio` it shows as `gpio-495 (wifi_pwr) out hi`.
  - This is the Duo S WiFi power/reset mapping; whether it matches Oz64's
    WL_REG_ON wiring is unverified. This is the prime suspect for the card
    not enumerating (wrong/missing power or pinmux on Oz64).

### Firmware path and gap

`aic8800_bsp.ko` hardcodes its firmware directory:

```
/usr/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80
```

and requests names such as `fmacfw_8800dc.bin`, `fw_adid_8800dc.bin`,
`fw_patch_8800dc.bin`, `fw_patch_table_8800dc.bin`, `lmacfw_rf_8800dc.bin`,
`fmacfw_patch_8800dc_u02.bin`, etc. `aic8800_fdrv.ko` wants
`aic_userconfig_8800dc.txt`.

On the board the two firmware dirs are:

- `/lib/firmware/aic8800_sdio/aic8800/` -> D80 + generic files
- `/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/` -> D80 + generic files

`find /lib/firmware -iname '*8800dc*'` returns **nothing**. No Realtek fw
either. So the AIC8800DC firmware/config is missing.

### Where the correct firmware lives upstream

`scpcom/aic8800-sdio-firmware` (a build input for the image) **does** have it,
pinned at commit `6314482`:
https://github.com/scpcom/aic8800-sdio-firmware/tree/6314482

- `aic8800/` — AIC8800 (old) + generic
- `aic8800D80X2/` — D80X2
- `aic8800DC/` — **the Oz64 chip**, e.g.
  - `aic_userconfig_8800dc.txt`
  - `fmacfw_patch_8800dc_u02.bin`, `fmacfw_patch_tbl_8800dc_u02.bin`
  - `fmacfw_calib_8800dc_u02.bin`, `fw_adid_8800dc_u02.bin`
  - `fw_patch_8800dc_u02.bin`, `fw_patch_table_8800dc_u02.bin`
  - `lmacfw_rf_8800dc.bin`
- `aic8800_and_aic8800D80/` — combined AIC8800 + D80

But `scripts/addons/aic8800-firmware/addon.mk` in this repo only copies:

```
$(...)/aic8800-sdio-firmware/aic8800/
$(...)/aic8800-sdio-firmware/aic8800_and_aic8800D80/
```

`aic8800DC/` is **not** copied. This looks like an oversight / incomplete
Oz64 support rather than an intentional exclusion.

## Possible fix paths

1. **Pragmatic (no rebuild):**
   - Install the missing `aic8800DC/*` blobs. Because `aic8800_bsp.ko` uses a
     single hardcoded dir, drop them into
     `/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/` (or verify from a
     fresh `strings` of the running bsp which path it selects per chip).
   - Then fix SDIO enumeration: confirm/enable the correct power/reset GPIO for
     AIC8800DC on Oz64 (the Duo S `wifi_pwr` hog may be the wrong pin), and
     re-check `mmc1` for a card. Without a card on the bus, no driver binds.

2. **Proper (rebuild):**
   - Add an `oz64` board config + DTS to this repo (correct SDIO pinmux, WiFi
     power/reg GPIO, board id), and patch `addon.mk` to also copy
     `aic8800DC/` into the aic8800 firmware dir.
   - Then `make BOARD=oz64 image` via the documented podman flow.

3. **Avoid onboard WiFi:** use a USB WiFi dongle (the image already ships
   many USB WiFi drivers under `/mnt/system/ko`).

## RESOLVED 2026-09-28 — onboard WiFi works

Two independent problems had to be fixed.

1. **CHIP_EN was never asserted.** The Oz64 schematic routes the
   AIC8800DC module `CHIP_EN` to net `WIFI_CHIP_EN`, which is the SG2000
   pad `AUX0` / `XGPIOA[30]` (Linux GPIO **510** with this DTB's bank A
   base of 480). The Duo S DTB instead hogs PA15 as `wifi_pwr`; on Oz64
   PA15 is `SPK_EN`, so the radio was never enabled and `mmc1` saw no
   card. Driving GPIO 510 high makes `mmc1` enumerate the card:
   `SDIO_ID=C8A1:C08D`.

2. **BT-over-SDIO wedges the SDIO bus.** With the card powered, loading
   the vendor `aic8800_fdrv.ko` (built with `CONFIG_SDIO_BT=y`) creates
   `wlan0` but then hangs the bus right after `btsdio_init()`. The last
   command sent is `TDLS_SDIO_BT_SEND_CFM` (msg id **3089**,
   `lmac_msg.h`), i.e. the BT-over-SDIO send path. From that point on
   `aicwf_sdio_hal_irqhandler` spins on reads returning `-110 /
   intstatus=ff`, flooding the log and wedging userspace (SSH dies while
   the serial console still works). The chip is an AIC8800DC; the
   scpcom driver's DC path appears never to have been exercised (Duo S /
   LicheeRV Nano use the D80 path).

### Fix applied

- **DTS**: replace the Duo S `wifi_pwr` PA15 hog with a `wifi_chip_en`
  hog on `&porta` GPIO 30, output-high (`configs/oz64/dts/`).
- **Driver**: build `aic8800_fdrv`/`aic8800_bsp` with
  `CONFIG_SDIO_BT=n` and `CONFIG_COEX=n`
  (`configs/chip/sg200x/patches/osdrv/0001-aic8800-disable-sdio-bt.patch`).
- **Firmware**: package the `aic8800DC` blobs and drop them into the
  driver's default single `aic_fw_path`
  (`/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/`);
  see `scripts/addons/aic8800-firmware/addon.mk`.

### Verified on hardware

- With GPIO 510 high and the rebuilt (BT-disabled) module:
  `wlan0` appears, **no IRQ storm**, SSH stays up.
- `iw dev wlan0 scan` returns real APs; associated to an open AP;
  `busybox udhcpc` obtained a lease; `ping -I wlan0 <gateway>` 0% loss.
- Link was weak in testing (~-81 dBm), so RTT was high, but it worked.

### Running-board persistence (test board only)

To make the currently-flashed Duo S image boot with WiFi without
rebuilding it:

- back up and replace
  `/mnt/system/ko/<kernel>/3rd/aic8800_fdrv.ko` with the rebuilt one;
- patch `/etc/init.d/S25wifimod` (the `load-wifimod` service) to assert
  `gpio510` and `echo 1 > /sys/class/mmc_host/mmc1/rescan` before
  `insmod`-ing the modules (the mmc host has already probed with no card
  by the time userspace runs, hence the rescan).

After a reboot this enumerates `mmc1`, autoloads the BT-disabled driver
and brings up `wlan0`. The built `oz64` image instead uses the DTB
`wifi_chip_en` hog, so the card is powered before the kernel mmc probe
and no boot-script change is needed.

### Note: building just the module off-tree

The image ships matching kernel headers, but Debian's riscv64 headers
contain **x86_64 host tools** (`fixdep`, `modpost`), are missing
`arch/riscv/kernel/vdso/Makefile`, and `syncconfig` needs flex/bison.
To rebuild only the fdrv natively:

- copy the headers to a writable dir;
- stub `arch/riscv/kernel/vdso/Makefile`;
- wrap `-mno-ldd` in `$(call cc-option,...)`;
- build `fixdep` and `modpost` with the board's gcc;
- configure with `CONFIG_SDIO_BT=n CONFIG_COEX=n CONFIG_VECTOR_0_7=n
  CONFIG_RISCV_ISA_THEAD=n
  CONFIG_TOOLCHAIN_NEEDS_EXPLICIT_ZICSR_ZIFENCEI=y KBUILD_MODPOST_WARN=1`.

The `oz64` board target (`make BOARD=oz64 image`) builds this correctly
with the container toolchain instead.

### Caveats

- Bluetooth is intentionally disabled on this board (WiFi only); the
  hardware is an AIC8800DC 2.4 GHz combo, so re-enabling BT would need a
  different fix/patch.
- A hardware watchdog (`/dev/watchdog0`, Synopsys DW, 21 s) is a handy
  dead-man switch while experimenting; `CONFIG_MAGIC_SYSRQ` and
  `CONFIG_DETECT_HUNG_TASK` are **off** in this kernel.

## Build-time configuration (2026-09-29)

The `oz64` target now takes optional make variables (see the README
"Build-time Configuration" section). They are baked onto the FAT boot
partition by the new `preconfigure` addon
(`scripts/addons/preconfigure/addon.mk`), which the runtime scripts already
read:

- `IMAGE_HOSTNAME` -> `/boot/hostname` (exact; wins over the device-key
  `prefix-hash`, which `S10uuid` regenerates each boot).
- `IMAGE_HOSTNAME_PREFIX` -> `/boot/hostname.prefix`.
- `WIFI_MODE=sta|ap|none`, `WIFI_SSID`, `WIFI_PASS`, `WIFI_IPV4_PREFIX`,
  `WIFI_WPA_CONF` -> `/boot/wifi.*` and `/boot/wpa_supplicant.conf`.
- `SECOND_CPU=camera|arduino` (default `arduino` on oz64): `arduino` sets
  `ION_SIZE=0`, which makes `chip.mk` zero the ISP/H26X/bootlogo regions and
  `S00kmod` skip the ISP/vcodec modules, leaving the C906L for the kernel
  remoteproc driver. `camera` keeps `ION_SIZE=74` plus `sensor-config`/`tpusdk`
  (Oz64 camera wiring is still a follow-up).

`S30wifi` was also fixed: the `echo -e "\t..."` lines were replaced with
`printf` so the generated `/etc/network/interfaces.d/wlan0` is valid under
`dash` (the earlier `echo -e` left literal `-e` prefixes).

Duo S-only addons were removed from the Oz64 config: `usb-switch` (it drives
GPIO 510, which on the Oz64 is the AIC8800DC `CHIP_EN`), `ethernet-leds`
(Duo S LED sysfs names) and `hciattach-uart` (Oz64 BT is SDIO and disabled).

Classic make caveat: a literal `$` in `WIFI_PASS` must be passed as `$$`.

Open station networks: leave `WIFI_PASS` unset. `S30wifi` now emits
`wpa-key-mgmt NONE` (and omits `wpa-psk`) when there is no password, so
`make BOARD=oz64 WIFI_MODE=sta WIFI_SSID=<open-ssid> image` joins without any
credential file. The `/boot/wpa_supplicant.conf` path was also fixed: `S30wifi`
now writes `wpa-conf /etc/wpa_supplicant.conf` for it (previously it only
copied the file and nothing referenced it).

## RESOLVED 2026-09-30 — WiFi auto-connect on the built image

First flash of the `oz64` arduino image booted and reached the network over
ethernet, but `wlan0` never associated even though the driver, firmware, SDIO
card (`mmc1:fe00`) and `/etc/network/interfaces.d/wlan0` (correct
`wpa-key-mgmt NONE` stanza) were all fine.

Root cause was a systemd/hotplug race, not the driver:

- `load-wifimod.service` insmods `aic8800_fdrv`, which creates `wlan0`; udev
  then fires `ifup@wlan0.service`.
- `wifi-builtin.service` runs `S30wifi` to write the `wpa-essid`/`wpa-psk`
  (or `wpa-key-mgmt NONE`) stanza, but it declared
  `Before=ifup@wifi0.service` — a **typo** (`wifi0` vs `wlan0`), so nothing
  ordered it before `ifup@wlan0`.
- Both started in the same second; `ifup@wlan0` read the default
  `iface wlan0 inet manual` stanza and never re-ran after `S30wifi` rewrote
  the file. `/run/network/ifstate` contained `wlan0=wlan0`, so ifup considered
  it done and `wpa_supplicant` was never started for the interface.

Fix: correct the typo in `scripts/addons/wifi-builtin/wifi-builtin.service`
and `wifi-mac.service` (`Before=ifup@wlan0.service`). Verified on the board:
after reboot `wifi-builtin` finished before `ifup@wlan0` started and `wlan0`
associated automatically (`wpa_state=COMPLETED`, DHCP `192.168.2.202`).

Manual confirmation that the config itself was never the problem:
`sudo ifdown wlan0 && sudo ifup wlan0` associated instantly.

## 2026-09-30 — antenna, per-interface names, deterministic IPv6

### The Oz64 has no onboard WiFi antenna
It uses a tiny external **u.FL / IPEX MHF1 (Gen 1)** receptacle (schematic part
`ZX-RF-3-Z1.30.85X`, ~3.0 mm across — a W.FL/MHF3 would be ~55% smaller). With
no antenna connected the radio is into an open port: it associates but sits
around -77…-83 dBm and can't pass data. Attaching a 2.4 GHz u.FL antenna
(VisionFive 2 pigtail works) took it to ~-53 dBm and 0% loss. Note: Gen-1
(u.FL/MHF1) ≠ Gen-3 (W.FL/MHF3) ≠ Gen-4 (MHF4); they don't intermate, and
Amazon mostly stocks Gen-1/Gen-4 while Gen-3 is niche.

### Distinct DHCP hostnames per interface
With `IMAGE_HOSTNAME` set, `scripts/addons/preconfigure/addon.mk` now appends to
`/etc/dhcpcd.conf`:

```
interface wlan0
	hostname <name>-wifi
nohook hostname
```

so ethernet keeps `<name>` and WiFi advertises `<name>-wifi` in DHCPv4 option
12 and the DHCPv6 FQDN. Previously both NICs sent the same hostname, so the
router's DNS conflated them into one name with several (stale) A/AAAA records —
`resolvectl query <name>` returned dead `fd86::` addresses, `ping <name>` failed
while `ping -4 <name>` and `<name>.local` worked. `nohook hostname` keeps
dhcpcd from renaming the system host from a lease (two dhcpcd instances, one per
NIC, otherwise race over `/etc/hostname`).

### Deterministic IPv6
`dhcpcd.conf` defaults (`slaac private`, DUID in `/var/lib/dhcpcd`) mint new
addresses over time/reflashes, so the router accumulated stale AAAA. The same
addon now sets `slaac hwaddr` and `duid ll` (EUI-64 / link-layer DUID from the
device-key-derived MACs), making the IPv6 addresses stable per device and
interface.

Deployment note: old stale records for the old name persist in the router until
their leases expire (or are cleared); and a board with both Ethernet and WiFi up
on the same subnet still exhibits normal multi-homing ARP behavior — running
only one link, or the per-interface names above, keeps it sane.

## 2026-10-08 — intermittent post-reboot WiFi loss; robustness + observability

Board `oz64-toad-30f4` associated to `cs4250` and served SSH, but after a later
reboot came up with neither `wlan0` nor `end0`, and the serial console showed
only the kernel banner (no login). Investigated from the SD card's persisted
journal:

- The image has **no `serial-getty@ttyS0`** (only `getty@tty1`) and boots with
  `loglevel=0`, so the serial console is boot-output only — there is no login
  prompt on `ttyS0` (the kernel console alone does not provide one). That is why
  the console looks dead after the kernel lines.
- The **last flushed boot actually succeeded**: `mmc1: new SDIO card`,
  `load-wifimod` created `wlan0`, it associated to `cs4250` and got DHCP
  (`192.168.8.199`); `multi-user`/`graphical` were reached. Userspace boot was
  ~57 s, mostly `dhcpcd` "waiting for carrier" on the cable-less `end0`.
- The failing boot's journal was **not flushed** before the power-off (journald
  default `SyncIntervalSec`), so its logs were lost.
- `wifi-builtin.service` only *writes* the config and `S25wifimod` is a bare
  `insmod` chain with no verification, so a transient failure on any given boot
  leaves WiFi down until the next reboot.

### Changes

- `configs/chip/sg200x/setup_rootfs.sh`: enable `serial-getty@ttyS0` (console
  login), set journald `Storage=persistent` + `SyncIntervalSec=10s` so the next
  failure is captured, and add `timeout 10` to `/etc/dhcpcd.conf` so a
  cable-less `end0` / slow association does not add ~30s each to the boot.
- `scripts/addons/load-systemko/S25wifimod`: rescan `mmc1` if the SDIO card is
  absent, then load the modules and verify `wlan0` appeared (bounded retry).
- `scripts/addons/wifi-builtin/wifi-builtin.service`: an `ExecStartPost` waits
  for `wlan0` and then forces `ifdown --force wlan0; ifup wlan0` with a few
  retries, instead of relying solely on the udev `ifup@wlan0` ordering.

### Debug notes

- To recover without U-Boot, pull the SD and read the rootfs read-only on a host
  (`debugfs`/`mtools`); the journal lives at
  `/var/log/journal/<machine-id>/system.journal`.
- A manual `booti` (bypassing the U-Boot flow) hit the same SD misdetect; that
  turned out to be the intermittent card issue below, not caused by `booti`.

## 2026-10-08 — the "no network after reboot" was a kernel panic (bad SD)

The intermittent "boots but nothing comes up" symptom (no WiFi, no Ethernet,
no console login) was **not** userspace or WiFi. A verbose boot (`loglevel=7`)
showed:

    mmc0: new SD card at address d555
    mmcblk0: mmc0:d555 SD032 30.6 MiB        # wrong capacity, no partitions
    VFS: Cannot open root device "mmcblk0p2" ... error -6
    Kernel panic - not syncing: VFS: Unable to mount root fs

The kernel intermittently **mis-enumerates the SD card**, so root
(`mmcblk0p2`) can't be mounted and the kernel panics. U-Boot reads the same
card fine (29.7 GiB, SDMA), so it's the kernel sdhci/ADMA path and/or a marginal
card. **Replacing the SD card fixed it** — the original card was bad.

The vendor U-Boot env sets `othbootargs=... loglevel=0`, which hides the panic
on the console (panic prints at KERN_EMERG, but a console loglevel of 0
suppresses it), so it looked like a silent hang. Fix: raise the loglevel and
regenerate the FAT env with `mkenvimage`, so warnings/errors/panics are visible.

If a known-good card still mis-enumerates, cap the kernel SD bus in the board
DTS: `&sd { no-1-8-v; max-frequency = <25000000>; };` and/or add
`no-sdio;`/`broken-cd;`. U-Boot reads it reliably, so the lower kernel bus
speed is the first lever.

## 2026-10-09 — regression: wifi-builtin left wlan0 DOWN

After the #6 WiFi changes, a boot could associate and get a DHCP lease
(`192.168.8.199/24`) and then end with `wlan0` **administratively DOWN** with the
lease still present (`ip a`: `<BROADCAST,MULTICAST> ... state DOWN`), so
`ping` said "Network is unreachable". The journal showed:

    wpa_supplicant[1211]: wlan0: CTRL-EVENT-TERMINATING
    ifup[1309]: ifup: interface wlan0 already configured

Cause: `wifi-builtin.service`'s `ExecStartPost` (added in #6) ran
`ifdown --force wlan0; ifup wlan0`. `ifdown` tore down the working link and
killed its `wpa_supplicant`; the subsequent `ifup wlan0` returned success with
"already configured" (ifupdown `/run/network/ifstate` still listed wlan0)
without bringing the link back up. Running `ifup wlan0` by hand hits the same
no-op; recovering needs `ifdown --force wlan0; rm -f /run/network/ifstate;
ifup wlan0`.

Fix: remove the `ExecStartPost` entirely. The original race (#6) is already
handled by the unit ordering — `wifi-builtin.service` (which writes
`/etc/network/interfaces.d/wlan0`) is `Before=ifup@wlan0.service`, so the
udev-triggered `ifup@wlan0` always reads the correct config. Verified with
several reboot cycles: `wlan0` comes up with `192.168.8.199/24` every boot.

(Reordering `wifi-builtin` to run before `load-wifimod` — "write config before
wlan0 exists" — is unnecessary and collides with `wifi-mac.service`'s
`Before=wifi-builtin`, so it was not done.)
