# Pine64 Oz64 on the Sophgo SG200x Debian image

Notes gathered 2026-09-27 while trying to get the onboard WiFi working on a
Pine64 Oz64 running scpcom's Duo S Debian image.

## TL;DR

- There is **no Oz64-specific Linux image** anywhere. The "Oz64 Debian" that
  RuyiSDK tests is literally scpcom's Milk-V **Duo S** image
  (`duos-e_sd.img.lz4`), which is what this board is already running.
- Onboard WiFi does not work because:
  1. The AIC8800 driver fails at bring-up
     (`aicbsp: fail to set AIC_WIFI power state to 1`) and never creates
     `wlan0`. The SDIO WiFi card never enumerates (`mmc1` has no card).
  2. Even if it enumerated, the image ships **no AIC8800DC firmware**. Oz64
     uses an **AIC8800DC**; the image only carries AIC8800 / AIC8800D80 blobs.
- The upstream firmware repo `scpcom/aic8800-sdio-firmware` **does** now
  contain an `aic8800DC/` directory, but the image build (`addon.mk`) only
  installs `aic8800/` and `aic8800_and_aic8800D80/`. So the correct blobs are
  never packaged.

## Board / hardware facts

- Board: Pine64 **Oz64**, SoC **Sophgo SG2000** (RISC-V C906 + Arm A53 + 8051).
- WiFi/BT: **AIC8800DC** (2.4 GHz WiFi6, BT 5.2). Confirmed by the PINE64 wiki
  + datasheet links:
  - https://wiki.pine64.org/wiki/Oz64
  - AIC8800DC datasheet linked from
    https://pine64.org/documentation/Oz64/Datasheets/
- Ethernet: 10/100 via `end0`. USB gadget NIC via `usb0`.

## What the running system actually is

- Image: scpcom `sophgo-sg200x-debian`, release **v1.9.13**
  (`/boot/ver` = `duos-e_sd-v1.9.13.img`).
  - https://github.com/scpcom/sophgo-sg200x-debian/releases
- Kernel: `5.10.260-20260911-7+duos` (riscv64). `loglevel=0` on the cmdline,
  so a lot of early boot dmesg is quiet.
- Device tree model: **`Milk-V DuoS`** (`compatible = cvitek,cv181x`).
  So the board is booting the Duo S DTB, not an Oz64 DTB.
- `/boot/board` says `id=maixcam name=MaixCAM` (generic/default board id from
  the shared packaging — not meaningful for this board).
- Rootfs: `/dev/mmcblk0p2` ext4 rw, `/boot` on `/dev/mmcblk0p1` vfat.
- `/mnt/system/ko/5.10.260-20260911-7+duos/3rd/` holds the vendor kernel
  modules (loaded by `/etc/init.d/S25wifimod`).

## Side quest: hostname resets on reboot

Not WiFi, but figured out here: `/etc/init.d/S10uuid` runs every boot and
rewrites `/etc/hostname` (and `/etc/hosts`) from a device-key hash:

```
prefix=duos                       # from /boot/hostname.prefix
new_hostname=${prefix}-$(sha512sum /device_key | head -c 4)
```

So editing `/etc/hostname` is pointless. Persistent overrides:

- Full hostname: `echo NAME | sudo tee /boot/hostname`
- Just the prefix: `echo PREFIX | sudo tee /boot/hostname.prefix`

Same script also sets the ethernet MAC (`/boot/eth.mac` overrides).

## WiFi investigation details

### Interfaces / modules

- `ip link`: only `lo`, `end0`, `usb0`, `tunl0`. **No `wlan0`.**
- `lsmod`: `aic8800_bsp`, `8733bs`, `cfg80211`.
- Module identities (from `riscv64-linux-gnu-strings`):
  - `aic8800_bsp.ko` -> `description=AIC BSP`
  - `aic8800_fdrv.ko` -> `description=RivieraWaves 11nac driver for Linux cfg80211`
  - `8733bs.ko` -> `description=Realtek Wireless Lan Driver` (i.e. **RTL8733BS**,
    a Realtek part; irrelevant to Oz64 — it's a Duo S variant option).

### Boot failure

`dmesg` shows the AIC BSP failing to power up the WiFi subsystem:

```
aicbsp: aicbsp_set_subsys, subsys: AIC_WIFI, state to: 1
aicbsp: aicbsp_platform_power_on
aicbsp: aicbsp_set_subsys, fail to set AIC_WIFI power state to 1
AICWFDBG(LOGERROR)  rwnx_mod_init, set power on fail!
```

- `aic8800_fdrv` is **not** present in `lsmod` afterwards -> it failed and
  unloaded. `8733bs` stayed loaded but is for the wrong silicon.
- `aic8800_bsp` has no gpio/ioremap/regulator imports (only `sdio_*`), so its
  "platform power on" is ultimately gated on the SDIO card being present /
  the host-side callback; with no card on `mmc1` it fails.

### No SDIO card

- `/sys/bus/mmc/devices/` contains only `mmc0:0001` (the microSD).
- `mmc1` (`wifi-sd@4320000`, alias points at the SDIO host) exists, driver
  `cvi`, but has **no card** and no `dmesg` lines.
- DT: `wifi-sd@4320000`, `compatible = cvitek,cv181x-sdio`, `status = okay`.
- DT has a **gpio-hog** named `wifi_pwr`, `output-high`, under
  `/proc/device-tree/gpio@03020000/gpio-controller@0/`.
  - In `/sys/kernel/debug/gpio` it shows as `gpio-495 (wifi_pwr) out hi`.
  - This is the Duo S WiFi power/reset mapping; whether it matches Oz64's
    WL_REG_ON wiring is unverified. This is the prime suspect for the card
    not enumerating (wrong/missing power or pinmux on Oz64).

### Firmware path and gap

`aic8800_bsp.ko` hardcodes its firmware directory:

```
/usr/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80
```

and requests names such as `fmacfw_8800dc.bin`, `fw_adid_8800dc.bin`,
`fw_patch_8800dc.bin`, `fw_patch_table_8800dc.bin`, `lmacfw_rf_8800dc.bin`,
`fmacfw_patch_8800dc_u02.bin`, etc. `aic8800_fdrv.ko` wants
`aic_userconfig_8800dc.txt`.

On the board the two firmware dirs are:

- `/lib/firmware/aic8800_sdio/aic8800/` -> D80 + generic files
- `/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/` -> D80 + generic files

`find /lib/firmware -iname '*8800dc*'` returns **nothing**. No Realtek fw
either. So the AIC8800DC firmware/config is missing.

### Where the correct firmware lives upstream

`scpcom/aic8800-sdio-firmware` (a build input for the image) **does** have it,
pinned at commit `6314482`:
https://github.com/scpcom/aic8800-sdio-firmware/tree/6314482

- `aic8800/` — AIC8800 (old) + generic
- `aic8800D80X2/` — D80X2
- `aic8800DC/` — **the Oz64 chip**, e.g.
  - `aic_userconfig_8800dc.txt`
  - `fmacfw_patch_8800dc_u02.bin`, `fmacfw_patch_tbl_8800dc_u02.bin`
  - `fmacfw_calib_8800dc_u02.bin`, `fw_adid_8800dc_u02.bin`
  - `fw_patch_8800dc_u02.bin`, `fw_patch_table_8800dc_u02.bin`
  - `lmacfw_rf_8800dc.bin`
- `aic8800_and_aic8800D80/` — combined AIC8800 + D80

But `scripts/addons/aic8800-firmware/addon.mk` in this repo only copies:

```
$(...)/aic8800-sdio-firmware/aic8800/
$(...)/aic8800-sdio-firmware/aic8800_and_aic8800D80/
```

`aic8800DC/` is **not** copied. This looks like an oversight / incomplete
Oz64 support rather than an intentional exclusion.

## Possible fix paths

1. **Pragmatic (no rebuild):**
   - Install the missing `aic8800DC/*` blobs. Because `aic8800_bsp.ko` uses a
     single hardcoded dir, drop them into
     `/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/` (or verify from a
     fresh `strings` of the running bsp which path it selects per chip).
   - Then fix SDIO enumeration: confirm/enable the correct power/reset GPIO for
     AIC8800DC on Oz64 (the Duo S `wifi_pwr` hog may be the wrong pin), and
     re-check `mmc1` for a card. Without a card on the bus, no driver binds.

2. **Proper (rebuild):**
   - Add an `oz64` board config + DTS to this repo (correct SDIO pinmux, WiFi
     power/reg GPIO, board id), and patch `addon.mk` to also copy
     `aic8800DC/` into the aic8800 firmware dir.
   - Then `make BOARD=oz64 image` via the documented podman flow.

3. **Avoid onboard WiFi:** use a USB WiFi dongle (the image already ships
   many USB WiFi drivers under `/mnt/system/ko`).

## RESOLVED 2026-09-28 — onboard WiFi works

Two independent problems had to be fixed.

1. **CHIP_EN was never asserted.** The Oz64 schematic routes the
   AIC8800DC module `CHIP_EN` to net `WIFI_CHIP_EN`, which is the SG2000
   pad `AUX0` / `XGPIOA[30]` (Linux GPIO **510** with this DTB's bank A
   base of 480). The Duo S DTB instead hogs PA15 as `wifi_pwr`; on Oz64
   PA15 is `SPK_EN`, so the radio was never enabled and `mmc1` saw no
   card. Driving GPIO 510 high makes `mmc1` enumerate the card:
   `SDIO_ID=C8A1:C08D`.

2. **BT-over-SDIO wedges the SDIO bus.** With the card powered, loading
   the vendor `aic8800_fdrv.ko` (built with `CONFIG_SDIO_BT=y`) creates
   `wlan0` but then hangs the bus right after `btsdio_init()`. The last
   command sent is `TDLS_SDIO_BT_SEND_CFM` (msg id **3089**,
   `lmac_msg.h`), i.e. the BT-over-SDIO send path. From that point on
   `aicwf_sdio_hal_irqhandler` spins on reads returning `-110 /
   intstatus=ff`, flooding the log and wedging userspace (SSH dies while
   the serial console still works). The chip is an AIC8800DC; the
   scpcom driver's DC path appears never to have been exercised (Duo S /
   LicheeRV Nano use the D80 path).

### Fix applied

- **DTS**: replace the Duo S `wifi_pwr` PA15 hog with a `wifi_chip_en`
  hog on `&porta` GPIO 30, output-high (`configs/oz64/dts/`).
- **Driver**: build `aic8800_fdrv`/`aic8800_bsp` with
  `CONFIG_SDIO_BT=n` and `CONFIG_COEX=n`
  (`configs/chip/sg200x/patches/osdrv/0001-aic8800-disable-sdio-bt.patch`).
- **Firmware**: package the `aic8800DC` blobs and drop them into the
  driver's default single `aic_fw_path`
  (`/lib/firmware/aic8800_sdio/aic8800_and_aic8800D80/`);
  see `scripts/addons/aic8800-firmware/addon.mk`.

### Verified on hardware

- With GPIO 510 high and the rebuilt (BT-disabled) module:
  `wlan0` appears, **no IRQ storm**, SSH stays up.
- `iw dev wlan0 scan` returns real APs; associated to an open AP;
  `busybox udhcpc` obtained a lease; `ping -I wlan0 <gateway>` 0% loss.
- Link was weak in testing (~-81 dBm), so RTT was high, but it worked.

### Running-board persistence (test board only)

To make the currently-flashed Duo S image boot with WiFi without
rebuilding it:

- back up and replace
  `/mnt/system/ko/<kernel>/3rd/aic8800_fdrv.ko` with the rebuilt one;
- patch `/etc/init.d/S25wifimod` (the `load-wifimod` service) to assert
  `gpio510` and `echo 1 > /sys/class/mmc_host/mmc1/rescan` before
  `insmod`-ing the modules (the mmc host has already probed with no card
  by the time userspace runs, hence the rescan).

After a reboot this enumerates `mmc1`, autoloads the BT-disabled driver
and brings up `wlan0`. The built `oz64` image instead uses the DTB
`wifi_chip_en` hog, so the card is powered before the kernel mmc probe
and no boot-script change is needed.

### Note: building just the module off-tree

The image ships matching kernel headers, but Debian's riscv64 headers
contain **x86_64 host tools** (`fixdep`, `modpost`), are missing
`arch/riscv/kernel/vdso/Makefile`, and `syncconfig` needs flex/bison.
To rebuild only the fdrv natively:

- copy the headers to a writable dir;
- stub `arch/riscv/kernel/vdso/Makefile`;
- wrap `-mno-ldd` in `$(call cc-option,...)`;
- build `fixdep` and `modpost` with the board's gcc;
- configure with `CONFIG_SDIO_BT=n CONFIG_COEX=n CONFIG_VECTOR_0_7=n
  CONFIG_RISCV_ISA_THEAD=n
  CONFIG_TOOLCHAIN_NEEDS_EXPLICIT_ZICSR_ZIFENCEI=y KBUILD_MODPOST_WARN=1`.

The `oz64` board target (`make BOARD=oz64 image`) builds this correctly
with the container toolchain instead.

### Caveats

- Bluetooth is intentionally disabled on this board (WiFi only); the
  hardware is an AIC8800DC 2.4 GHz combo, so re-enabling BT would need a
  different fix/patch.
- A hardware watchdog (`/dev/watchdog0`, Synopsys DW, 21 s) is a handy
  dead-man switch while experimenting; `CONFIG_MAGIC_SYSRQ` and
  `CONFIG_DETECT_HUNG_TASK` are **off** in this kernel.
